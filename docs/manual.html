TCS Design and Documentation

Warning

TCSpecial is an alpha release. It is not fully tested, it is not feature complete, and it is subject to rapid change. Until 1.0, any change to its API changes the minor version number (0.1 to 0.2), so a release that changes only the patch number never breaks code built against it. Feedback is welcome, even at this stage: open an issue at https://github.com/vomlehn/tcspecial/issues.

TCSpecial is telemetry and control, special, and it is flight software. It connects the devices aboard a vehicle -- on an I2C bus, a SPI link, a serial line, a CAN bus, a set of discrete lines, a socket or a device file -- to the places their data has to reach: the mission operations center, the MOC, on the ground, and software aboard that computes from it, keeps it, or sends it on. Every one of those is a node, and what joins two is a link, and both are read from a configuration file at startup, so what a particular vehicle does is a file.

The TCS software

TCSpecial is the hub of the TCS software. Everything else is built around it: the programs that write, check and test its configurations, the library a ground station uses to talk to it, and the projects it is built from. This page introduces all of them and links to their manuals.

Some of those projects are products in their own right, used with or without TCSpecial: tcs-xtce, its XTCE editor tcs-xtcee and its XTCE libraries, in every language they support, and tcslog and tcslog-tools. None of them needs TCSpecial; TCSpecial uses them.

In flight

A vehicle running tcspecial, and the ground station that commands it.

Aboard the vehicle, the TCSpecial Flight Executive, tcspecial, runs the payloads. Each payload is reached through an interface of its own -- I2C, SPI, a serial line, CAN, GPIO lines, a socket to a program aboard, and others -- and is a device node in the configuration's graph. Compute nodes vote between redundant sensors, convert units and run thermostats; a gateway node is the vehicle's end of the link to the ground. tcspecial keeps a record aboard of what it sent down, in a log written by the TCS Onboard Log, tcslog, a library of its own.

On the ground, a mission control system such as Yamcs (https://yamcs.org) holds the other end of the link through the TCSpecial MOC Correspondent, tcsmoc. Both ends share TCS Link Support, tcsprotocol, which says what goes on the link. tcsmoc sends the vehicle its commands, receives its telemetry and beacons, and knows from the vehicle's configuration where each datum arrives and what it is; Yamcs's mission database is generated from the same configuration, so the two ends cannot disagree about the link. The link's packets are packed and unpacked by code that tcs-xtce generates from their XTCE description. Back on the ground, tcslog-tools reads a log that has come down from the vehicle.

On a desktop

The same software, every connection made on one desktop.

None of it needs a vehicle. On one desktop, tcs-sim stands in for the payloads, on a physics model of the world they act on, and tcs-moc for the mission operations center, and between them runs the same tcspecial that flies. make runmocy starts all three on one configuration, and every connection in the figure above is made on the desktop: commands, telemetry and beacons over sockets on the loopback interface, and the devices as pseudo-terminals and loopback addresses that tcs-sim answers on a physics model of the payloads. A configuration can be developed, run and watched this way long before there is hardware to run it on, and parts of it moved to real devices one at a time.

A configuration is written with tcs-gui, which draws it as a diagram of nodes and links, and checked with tcs-verify, which says what is wrong with it without running any of it. Both read it through tcsprotocol, the library the vehicle and the ground share, so the error a person sees on the desktop is the one the vehicle would refuse the file with.

The link's XTCE can be read and edited with tcs-xtcee, the XTCE editor that comes with tcs-xtce, and every TCS project builds its packages with the make rules and scripts of tcs-helpers.

Production and non-production software

The TCS software is in two kinds, and its documents are divided the same way. Production software runs aboard the vehicle or in the mission operations center, and is written and reviewed as such; its names have a letter straight after tcs or tcslog: tcspecial, tcsmoc, tcslog. The rest -- the tools that write, check, simulate, test and build -- is non-production, and its names have a hyphen or an underscore there: tcs-gui, tcs-sim, tcslog-tools. Production software is built only from production software. See Production code and its names in the tcspecial design.

Read from a checkout, the links to the other TCS projects lead to their documents in a checkout of each beside this one, as the build expects (../tcs-xtce and so on); read on the web, to their published pages. Where neither has them, their repositories do: tcs-xtce, tcslog, tcslog-tools and tcs-helpers.

The manuals

Production software

The tcspecial manual
The TCSpecial Flight Executive, and what is common to all the programs: the configuration files and what each payload, computation and gateway in them says, the shipped examples, installing, running the programs together, the commands the vehicle answers to, the crates used and the license.
The TCSpecial libraries
tcsmoc, the TCSpecial MOC Correspondent, in the MOC, in Rust, and tcsmoc-c, its C interface; tcsprotocol, TCS Link Support, used aboard and in the MOC.
The tcslog manual
The TCS Onboard Log: the library that keeps telemetry aboard until there is a link to send it down.
The tcs-xtce manual, for tcsxtce
tcsxtce, tcs-xtce's runtime: what the packet code tcs-xtce generates runs on, and the digest two programs check each other's XTCE with. The manual is tcs-xtce's, and covers the compiler as well.
The tcs-ccsds manual
The CCSDS time codes, run aboard and on the ground; a chapter of the tcs-xtce manual.

Non-production software

The tcs-gui manual
The editor. tcs-gui draws a configuration and its simulator configuration as diagrams of nodes and links, checks them as they are edited, and writes them back.
The tcs-sim manual
The payload simulator. tcs-sim answers for a vehicle's payloads as their devices would; its manual also describes the simulator configuration that says how.
The tcs-moc manual
The simulated operations center. tcs-moc shows what the vehicle sends the ground, panel by panel and in plots, and sends it commands.
The tcs-verify manual
The checker. tcs-verify reads a configuration and says what is wrong with it, running none of it.
The tcs-xtce manual
The compiler from XTCE to Rust, C, C++ and Python, which generates the code that packs and unpacks the link's packets. The tcs-xtce manuals list it and the others below.
The tcs-xtcee manual
The XTCE editor.
The tcslog-tools manual
The programs that read a tcslog log on the ground.
The tcs-helpers README
The make rules and scripts the TCS projects share to build their packages, check their names and keep their pages up to date.
