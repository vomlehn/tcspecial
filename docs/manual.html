Warning

TCSpecial is an alpha release. It is not fully tested, it is not feature complete, and it is subject to rapid change. Until 1.0, any change to its API changes the minor version number (0.1 to 0.2), so a release that changes only the patch number never breaks code built against it. Feedback is welcome, even at this stage: open an issue at https://github.com/vomlehn/tcspecial/issues.

Tip

New to TCSpecial? Getting started installs the released packages and runs a vehicle, a simulator and a ground station on your desk, in about fifteen minutes.

Tip

A complete example, worked step by step: Building a vehicle is a document of its own that builds a small lunar lander's science deck in ten stages, from one payload to a whole vehicle -- payloads, computations, commands, rates, a vote, included files, a log aboard, a payload program and the gateway. Each stage is a configuration that tcs-verify passes and that runs on a desk, and a test keeps it so. Start there to see how the pieces fit together.

TCSpecial is telemetry and control, special, and it is flight software. It connects the devices aboard a vehicle -- on an I2C bus, a SPI link, a serial line, a CAN bus, a set of discrete lines, a socket or a device file -- to the places their data has to reach: the mission operations center, the MOC, on the ground, and software aboard that computes from it, keeps it, or sends it on. Every one of those is a node, and what joins two is a link, and both are read from a configuration file at startup, so what a particular vehicle does is a file.

The TCS software

TCSpecial is the hub of the TCS software. Everything else is built around it: the programs that write, check and test its configurations, the library a ground station uses to talk to it, and the projects it is built from. This page introduces all of them and links to their manuals.

Some of those projects are products in their own right, used with or without TCSpecial: tcs-xtce, its XTCE editor tcs-xtcee and its XTCE libraries, in every language they support, and tcslog and tcslog-tools. None of them needs TCSpecial; TCSpecial uses them.

In flight

A vehicle running tcspecial, and the ground station that commands it.

Aboard the vehicle, the TCSpecial Flight Executive, tcspecial, runs the payloads. Each payload is reached through an interface of its own -- I2C, SPI, a serial line, CAN, GPIO lines, a socket to a program aboard, and others -- and is a device node in the configuration's graph. Compute nodes vote between redundant sensors, convert units and run thermostats; a gateway node is the vehicle's end of the link to the ground. tcspecial keeps a record aboard of what it sent down, in a log written by the TCS Onboard Log, tcslog, a library of its own.

On the ground, a mission control system such as Yamcs (https://yamcs.org) holds the other end of the link through the TCSpecial MOC Correspondent, tcsmoc. Both ends share TCS Link Support, tcsprotocol, which says what goes on the link. tcsmoc sends the vehicle its commands, receives its telemetry and beacons, and knows from the vehicle's configuration where each datum arrives and what it is; Yamcs's mission database is generated from the same configuration, so the two ends cannot disagree about the link. The link's packets are packed and unpacked by code that tcs-xtce generates from their XTCE description. Back on the ground, tcslog-tools reads a log that has come down from the vehicle.

On a desktop

The same software, every connection made on one desktop.

None of it needs a vehicle. On one desktop, tcs-sim stands in for the payloads, on a physical model of the world they act on, and tcs-moc for the mission operations center, and between them runs the same tcspecial that flies. make runmocy starts all three on one configuration, and every connection in the figure above is made on the desktop: commands, telemetry and beacons over sockets on the loopback interface, and the devices as pseudo-terminals and loopback addresses that tcs-sim answers on a physical model of the payloads. A configuration can be developed, run and watched this way long before there is hardware to run it on, and parts of it moved to real devices one at a time.

A configuration is written with tcs-cfge, which draws it as a diagram of nodes and links, and checked with tcs-verify, which says what is wrong with it without running any of it. Both read it through tcsprotocol, the library the vehicle and the ground share, so the error a person sees on the desktop is the one the vehicle would refuse the file with.

The link's XTCE can be read and edited with tcs-xtcee, the XTCE editor that comes with tcs-xtce, and every TCS project builds its packages with the make rules and scripts of tcs-helpers.

The manuals

The manuals and the design documents are grouped by the category of software each is about, from operational code, which flies or runs the MOC, to the tools around it: see The categories of TCS software at the end of this page.

Read from a checkout, the links to the other TCS projects lead to their documents in a checkout of each beside this one, as the build expects (../tcs-xtce and so on); read on the web, to their published pages. Where neither has them, their repositories do: tcs-xtce, tcslog, tcslog-tools and tcs-helpers.

Software tools

The tcs-cfge manual
The editor. tcs-cfge draws a configuration and its simulator configuration as diagrams of nodes and links, checks them as they are edited, and writes them back.
The tcs-verify manual
The checker. tcs-verify reads a configuration and says what is wrong with it, running none of it.
The tcs-conflict manual
Whether two configurations can be run at once: tcs-conflict says what both want -- a port, a device, a state file -- with the lines that say so.
The tcs-xtce manual
The compiler from XTCE to Rust, C, C++ and Python, which generates the code that packs and unpacks the link's packets. The tcs-xtce manuals list it and the others below.
The tcs-xtcee manual
The XTCE editor.

Verification tools

The tcs-sim manual
The payload simulator. tcs-sim answers for a vehicle's payloads as their devices would; its manual also describes the simulator configuration that says how.
The tcs-moc manual
The simulated operations center. tcs-moc shows what the vehicle sends the ground, panel by panel and in plots, and sends it commands.
The TCS test container
A Kubuntu or Fedora system in a container, in which the TCS packages are installed and tried as an administrator would, without touching the machine it runs on: container/bin/start starts it, made from scratch with the newest packages built the first time or with --rebuild, and opens a shell in it, where tcsx runs an example, cfge edits a configuration in tcs-cfge and xtcee edits XTCE in tcs-xtcee.

The categories of TCS software

The manuals and design documents above are grouped by the category of TCS software each is about. Every TCS project puts each of its directories in one of six categories, and says which in a categories.toml at its top:

Operational code
What a mission depends on while it operates, aboard the vehicle or in the mission operations center, written and reviewed as such: tcspecial, tcsmoc, tcsprotocol, tcsverify, tcsapp, tcslog, tcsxtce and tcsccsds. It is built only from operational code.
Software tools
What makes or checks what operational code is built from or loads: the tcs-xtce compiler, which generates the link's packet code; tcs-cfge and tcs-xtcee, which write configurations and XTCE; tcs-verify, which checks them; and tcs-diagram and tcs-ui, which they draw with. They take the most care of all but operational code, since a mistake in what they make or pass reaches a vehicle with no fault in the operational code.
Verification tools
What is used only to test: tcs-sim, which stands in for the payloads, tcs-moc, which stands in for the MOC, the test apps, the test container, and every test.
Infrastructure
What builds, packages, documents and checks the rest: tcs-helpers, each project's makefiles and install-tools, its CI and its pages.
Analysis tools
What works on what a mission produced: tcslog-tools, which reads a log once it is on the ground.
Examples
What is there to show how the rest is used: each project's examples, and the guide's lander.

The names follow DO-178C's where they can, though its "software tools" are every tool, verification tools among them, and here they are the others.

A name says whether code is operational: a letter, or nothing, straight after tcs or tcslog (tcspecial, tcsmoc, tcslog) is operational code's, and a hyphen or an underscore there (tcs-cfge, tcs-sim, tcslog-tools) is any other category's. Each project's make operational-names holds its names and its categories.toml to each other. See Operational code and its names in the tcspecial design for the requirements, and Code categories in tcs-helpers' README, which defines the categories for every TCS project.
