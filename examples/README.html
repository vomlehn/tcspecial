Examples

Each example is a directory holding three files:

  • <name>.ytcs is a tcspecial configuration.
  • <name>.xtcs is the same configuration in XML.
  • <name>-sim.yaml is the tcssim configuration that simulates its payloads.

An example whose payload is a program of its own holds that program too, beside those files: simple-app does, with a Python 3 payload and a Rust ground station. An example may hold a ground program without holding a payload: beacon does, its ground station watching something tcspecial sends on its own account, and so does ping, whose ground station is Python 3.

Two examples that are one example with another ground station share what they have in common from a directory of its own, which is not an example and holds no configuration: ping-common holds the ping link and the window that ping and ping-yamcs both show, and thermostat-common the physics model the simulator files of thermostat and thermostat-yamcs both name. What a file cannot refer to – a simulator file includes no other, and a ground station in Python reads no configuration includes – is written in both, and a test holds the two copies to each other: examples/thermostat-yamcs/tests/shared.rs. yamcs-common is not an example either: it is the Rust the tests of the examples through Yamcs share.

A configuration and its simulator file are matched by payload name. The simulator file can’t name a payload the configuration doesn’t have, nor one the simulator would not stand in for: a payload that is a program, which tcspecial runs itself. tcsverify refuses either, as tcssim does. A payload that is only driven, such as tees’ heater, is simulated like any other: its stand-in counts what the vehicle sends it.

The YAML and XML files must say the same thing, so change both together.

Every payload a simulator file names says simulate: true – itself or in its group, not both – for tcssim to stand in for it; simulate: false would leave it to the real device. Every simulator file also has a tcssim section giving the address at which tcssim says it has made its stand-ins, a port no other example uses, so that tcsmoc starts tcspecial only once they are there. The make run-* targets give every program --simulate=all, the run being one with stand-ins only: a program started without --simulate gets the flight setting, none, and refuses every stand-in. See “Stand-ins or hardware” in the manual.

The examples’ programs – beacon, lorem_gateway and ping_gateway.py – are quiet unless given -v or --verbose: they print what they are for and any error, and with the flag they also say what they are doing, such as where they are listening. A tcspecial one of them starts is started --quiet, so that its startup summary does not fill the console, unless the program was given -v itself; whatever stops tcspecial starting is said either way.

They also take --yaml or --xml, but not both, saying which of the example’s two configuration files to read. With neither, beacon and lorem_gateway read the YAML and ping_gateway.py the XML. A file named on the command line beside one of the two has to be the spelling it asks for, and a vehicle the program starts reads the same file.

Two sets of tests find the examples on their own, so adding one means adding its directory here, and a row to the table of its section below; there’s no list in the tests to update:

  • tcsverify/tests/examples.rs runs tcsverify on each configuration and its simulator file (any error or warning fails), and checks that the YAML and XML read as the same configuration.
  • tcsgui/tests/schema.rs validates each XML file against tcspecial.xsd, checks each YAML key against tcspecial.schema.json, and checks that every file names its schema (../../tcsgui/share/schema/...).

make in this directory builds README.html from this file, with style.html in its head – which is where the tables’ cells are told to sit at the top of their row, markdown having no way to say so. make help lists the targets, including the ones that run tcspecial on each example.

Simple examples

Each shows one thing at its simplest: a payload’s data reaching the ground, the vehicle saying it is alive, the vehicle answering a ping. Start with minimal, the smallest configuration that does anything.

Directory Description
minimal The smallest working configuration: one UDP payload whose telemetry goes straight to the ground (MOC).
beacon The one thing a ground station knows without asking: a window showing the spacecraft’s beacon, built from the two halves any ground station would use – tcslib::beacon to listen and tcsui’s panel to show it.
ping The ground pings a ping vehicle node and times the answer: the round trip, and the two halves of it. The ground station is Python 3, with the beacon panel and the halves it is built from written again in Python under python/, and tests that hold them to the Rust.
ping-yamcs The ping example with Yamcs between the ground station and the vehicle: a gateway_yamcs gateway puts a CCSDS primary header on every packet to and from the ground, the beacon included, and ping_yamcs.py runs Yamcs on tcspecial’s own XTCE and pings through it from the ping example’s window. Needs a Yamcs release unpacked somewhere.
tees The four nodes that do nothing to what passes: a tee-gateway sends each command on to a heater and back to the ground, a tee-payload sends each reading to the ground and on aboard, and a null-gateway and a null-payload drop what they are sent. tcspecial/tests/tees.rs flies it.
fprime A vehicle that answers to an F´ flight computer rather than to the ground: a gateway_fprime node sends each reading, the temperature a to_kelvin node makes of it and what a hysteresis node decides of that, to the deployment’s bridge component at its bridge_base, and takes the bridge’s commands on to a heater. tcspecial/tests/fprime.rs flies it, and make fprime-test runs the bridge itself, in fprime/, against it.
cfs A vehicle that answers to a cFS flight computer: tcspecial joins its software bus as an SBN peer, a gateway_cfs node publishes each reading as its tlm_base plus the reading’s device id, and a command published as its cmd_msgid goes on to a heater. Every link is carried over the one peer, as message IDs. make run-cfs runs tcsmoc on it, tcssim standing in for the cFS side; tcspecial/tests/cfs.rs flies it against a test playing the cFS side, and tcspecial/tests/cfs_ground.rs commands it from tcslib.

minimal

The smallest configuration that does anything: one payload, sensor, a program on this host at 127.0.0.1:5001 that sends its readings over UDP. Nothing is drawn from it, so its readings go to the ground over the tcspecial section’s payload_telemetry: tcspecial sends each one to dest_base plus the payload’s device id, 127.0.0.1:6100 for sensor, which is device 0. tcssim stands in for sensor, sending a packet every second.

make run-simple

That runs tcsmoc on the example, which starts tcspecial and tcssim itself and shows a panel for sensor: when its last packet arrived, what it said, and how many there have been.

Languages:

  • MOC: Rust – tcsmoc.
  • Vehicle: Rust – tcspecial.
  • Payload: Rust – tcssim stands in for sensor, a network payload.

beacon

What a ground station can know about a spacecraft without asking it anything. tcspecial sends a beacon every beacon.default_interval for as long as it runs, over a socket of its own, whether or not anything has connected to it – so this example commands nothing and still says whether the vehicle is alive, which build it is, and whether the configuration it is serving is the one the ground read.

It is also the example of how a ground program is put together, because almost nothing in it is its own:

  • tcslib::beacon binds the socket, reads each datagram, counts the beacons that did not arrive, compares the digest in each one with the ground’s own and says how stale the last one is. No window, no toolkit: a ground station with no screen – a logger, a test – uses exactly this.
  • tcsui holds the panel, as markup other windows import, and works out what to show on it: which colour the indicator is, and the two lines beside it.
  • beacon, the program here, reads the configuration to find where the beacons are, starts the loop on a thread, and puts each pass in the window. That is all of it, but for a button.

A beacon is a line of text, six fields with a colon between each: the name tcspecial, the version as major.minor.patch, the configuration’s MD5 digest in lower-case hex, the beacon’s number in decimal, restart while a restart the ground commanded is under way and the MOC has not connected since or normal otherwise, and the interface’s digest in hex:

tcspecial:0.1.0:36999e46a4bf436854442d8f97a2248d:42:normal:0123...cdef

It is text so that it can be read as it is, in a packet capture or with any UDP listener. tcspecial writes every beacon and tcslib::beacon reads it with tcslibgs::Beacon, and this example’s test writes the beacon it sends the same way. The window shows it differently, as tcspecial v0.1.0 md5 <digest>.

After the indicator, on its Status: row, is the stage the indicator is at, in a word: Unheard before any beacon has arrived, Heard while beacons are arriving, Aging once several are missing, and Waiting once nothing is being heard. It changes as the stage does.

The window is white, as the ping example’s is, and its button is drawn the way that window draws its own.

The button starts tcspecial on the same configuration and stops it, so that the indicator can be watched coming on with the first beacon and going out after the last. The window opens with it saying Start tcspecial, because tcspecial is not running. Pressed, it starts tcspecial and says Stop tcspecial; pressed again, it stops tcspecial with kill() and says Start tcspecial, which is where it began. tcspecial is the binary beside beacon, run directly rather than through cargo run, so that the kill stops tcspecial itself. Closing the window stops it as well, and so does the watcher dying, which the kernel is told to see to; and a tcspecial that stops by itself puts the button back to Start tcspecial.

tcsmoc shows the same panel from the same library, in a row beside its command link, which is the point of their being apart: an operator who has read one has read the other.

The beacon’s ports are this example’s own – a hundred above the ones the other examples use – so the watcher can be left running while another example is looked at. It opens a window, so it wants a display.

make run-beacon

That builds tcspecial and the watcher and opens the window, and tcspecial starts when the button is pressed. Without make:

cargo build --bin tcspecial --bin beacon
cargo run --bin beacon               # beacon.ytcs
cargo run --bin beacon -- --xml      # beacon.xtcs

Languages:

  • MOC: Rust – the beacon program, on tcslib::beacon and tcsui.
  • Vehicle: Rust – tcspecial.
  • Payload: Rust – tcssim stands in for sensor, a network payload.

ping

The ground sends a ping up to the gateway node, which hands it to the ping node; the ping node answers with the vehicle’s time on the end, and the answer comes back down. What a ping and its answer say is tcslibgs::node::vehicle::ping:

ping #<count> <seconds>.<nanoseconds>                    up
ping #<count> <seconds>.<nanoseconds> <seconds>.<nanoseconds>   down

The ground station, ping_gateway.py, is Python 3 and uses nothing outside the standard library to read its configuration’s XML, the default; with --yaml it reads the YAML instead, which needs PyYAML (python3-yaml on Debian and Ubuntu). Its window shows the beacon panel, the last ping sent and when, the last answer and when, and three times: the round trip, MOC to tcspecial, and tcspecial to MOC. The last two are each read across two clocks, so each includes their offset and may be negative; their sum is the round trip. Press Send ping to send one: it clears the time received until its own answer, matched by count, arrives.

It is built the way the beacon program is, from the same two halves written again in Python: python/tcslib/beacon.py after tcslib::beacon, python/tcsui/beacon_panel.py after tcsui, and python/tcslibgs for the ping format, the beacon and the configuration. The interface digest beacons are checked against is worked out with tcs-xtce’s Python runtime, from the tcs-xtce checkout beside this tree. ping-common/ping_ground.py is the ping’s own part, with no window, and ping-common/ping_window.py the window, both shared with ping-yamcs. The Rust crate beside them is the tests that hold the Python to the Rust; cargo test runs them.

make run-ping                                   # the vehicle and the window
python3 examples/ping/ping_gateway.py --pings 3 # no window: three pings
python3 examples/ping/ping_gateway.py --yaml    # ping.ytcs, not ping.xtcs

It sends a CONNECT of its own as soon as the vehicle is started, carrying the configuration’s checksum, with python/tcslib/listening.py, and again each second until the vehicle answers with that checksum: a vehicle sends nothing down, the ping node’s answers included, until it has taken one. --pings waits for it before the first ping; -v says when it is matched. It is sent from the configuration’s tcs_cmd.send, so tcsmoc cannot be run on the same configuration beside it.

ping_gateway.py starts the vehicle itself: tcspecial from the build, on the same configuration. It kills it when it exits, however it exits – if it is killed or crashes, the kernel is told to kill tcspecial – so a vehicle is running exactly while its ground station is. Build tcspecial first (make run-ping does). To run the vehicle yourself, in another terminal, say --no-vehicle:

cargo run --bin tcspecial -- examples/ping/ping.xtcs   # in one terminal
python3 examples/ping/ping_gateway.py --no-vehicle    # in another

Its ports are all in the seven thousands, which no other example uses.

tcsmoc pings it too: make runmocy TCSPECIAL_CONFIG_FILE=examples/ping/ping, then the Ping node button beside Command. It is the same panel, kept by tcslib::ping, which ping_ground.py is written after.

Languages:

  • MOC: Python 3 – ping_gateway.py, on python/; or Rust, in tcsmoc.
  • Vehicle: Rust – tcspecial, whose ping node answers.
  • Payload: none. The ping node is the vehicle’s own, and nothing is simulated.

ping-yamcs

The ping example with Yamcs at the ground end. The vehicle and what is timed are the same; what differs is the configuration’s gateway, yamcs, so every packet to and from the ground carries a CCSDS primary header, which tcspecial adds as each goes and takes off as each arrives:

What Which way APID
the beacon down beacon.apid, 0x100
CONNECT and its answer up, down tcs_cmd.apid, 0x101
a ping up the gateway node’s apid_base, 0x200
its answer down apid_base plus the ping node’s device id, 0x201

A payload nothing in the drawing touches would report as telemetry of payload_telemetry.apid_base, 0x300, plus its device id. This vehicle has none, so Yamcs is given no container for one – until one is added to the configuration, when it is.

ping_yamcs.py writes a Yamcs configuration from the tcspecial one – the ports and the APIDs, stated once – with a mission database of tcspecial’s own XTCE and a wrapper that puts the header around it. The wrapper and Yamcs’s links are generated by python/tcslibgs/yamcs.py: a container named after each node whose data reaches the ground, pingPacket here; a command for each gateway node; and a link on every port. The ping node has an interface document of its own, tcslibgs/xtce/ping.xtce, which states a ping and its answer field by field – the prefix ping #, the count, the seconds and the nine digits of nanoseconds, and for the answer the space and the vehicle’s time – so pingPacket holds the answer as those fields, ReplyCount, ReplySentSeconds and the rest, and the gateway node, whose data goes only to the ping node, takes the document’s command, Ping, with the arguments Count, SentSeconds and SentNanoseconds. Yamcs’s web interface shows both as the text they are. A node with no such document is given its data whole, as a binary parameter named after it, and a gateway node whose data goes anywhere else a command named after it that carries its data whole. Nothing in the wrapper is written by hand per APID, so a node added to the configuration is decoded by Yamcs the next time the example runs, and no line of it is wider than 80 columns. A node whose data the configuration types – a conversion’s or a vote’s value in its unit, a thermostat’s decision – is given a parameter of that type instead: see thermostat-yamcs. It starts Yamcs and tcspecial, has Yamcs send CONNECT until the vehicle answers with the configuration’s checksum, then pings through Yamcs – the ping split into the document’s fields by the code tcs-xtce generates from it, python/tcslibgs/ping_packet.py – and reads the answers back over Yamcs’s REST API, putting each together again from its fields.

Its window is the ping example’s, from ping-common: the beacon panel, and the ping panel with its Send ping button. Starting Yamcs, its REST API, CONNECT and the beacon through Yamcs are python/tcslib/yamcs_ground.py’s, which thermostat-yamcs shares. The beacon panel is fed the beacon’s own bytes, which the Yamcs wrapper keeps whole as the BeaconBody parameter, so it checks the configuration’s checksum and the beacon’s number and ages the indicator just as the ping example’s does. With --pings there is no window: it prints the first beacon and each exchange, and stops.

make run-ping-yamcs YAMCS_HOME=~/yamcs-5.14.0     # the window
python3 examples/ping-yamcs/ping_yamcs.py --yamcs ~/yamcs-5.14.0 --pings 3
python3 examples/ping-yamcs/ping_yamcs.py --describe   # what it read

Yamcs and tcspecial are stopped when the window is closed or the pings are done, and are killed with ping_yamcs.py if it is killed or crashes, so neither is left holding the example’s ports.

An answer’s arrival time is when Yamcs received it, to the millisecond, as finely as Yamcs says; so a half of a sub-millisecond round trip can come out a fraction of a millisecond negative.

The Rust crate beside it is its tests, which cargo test runs: agrees.rs holds the ports, APIDs and checksum ping_yamcs.py --describe reads from ping-yamcs.xtcs to what tcslibgs reads from ping-yamcs.ytcs, and the generated wrapper’s APIDs, for the example and for a copy with more nodes, to the ones tcslibgs counts; wrapper.rs works the generated wrapper as Yamcs would, decoding the beacon, the answers – a ping’s field by field, every byte of it read – and each added node’s data as the vehicle frames them, and encoding CONNECT and a ping, its fields as text, for the vehicle to unframe and read as the ping tcslibgs writes, with the interpreter of examples/yamcs-common; and python.rs runs test_ping_yamcs.py, which also holds every line of the written wrapper to 80 columns. None needs Yamcs or opens a window.

YAMCS_HOME is where a Yamcs release is unpacked, holding bin/yamcsd; https://github.com/yamcs/yamcs/releases has them, and it was written against 5.14.0. Yamcs’s web interface is at http://localhost:16090 meanwhile, showing every packet and parameter.

Yamcs sends its commands from a port the system chooses and takes the answers on the same socket, so the configuration’s tcs_cmd.send is 127.0.0.1:0: commands from any port of this host.

Its ports are all in the sixteen thousands, which no other example uses.

Languages:

  • tcspecial configuration: YAML (ping-yamcs.ytcs) or XML (ping-yamcs.xtcs)
  • Yamcs configuration: YAML templates (python/tcslib/yamcs-templates) and an XTCE template (python/tcslibgs/yamcs.xtce)
  • ground program: Python 3 (ping_yamcs.py), with Yamcs (Java)

Payloads the kernel stands in for

Each is one of the payload types whose far end is a device the kernel makes rather than a file or a socket tcssim can make, and each is flown against the kernel’s own stand-in for that device by tcspecial/tests/kernel-stand-ins.rs, which plays the device’s far end through the kernel: that is what makes CAN and GPIO supported. IIO stays experimental until its test has passed, which it cannot on a kernel whose iio_dummy has no buffer, such as Ubuntu’s: see “What Is Supported and What Is Experimental” in docs/design.rst. The devices need root to make, so nothing here makes them. Run this once, from the account that runs the examples and the tests:

sudo bin/mk-kernel-stand-ins

With no arguments it makes the CAN bus and the GPIO chip; sudo bin/mk-kernel-stand-ins iio makes the IIO sensor, and can gpio iio all three. It refuses, and makes nothing, where this kernel lacks a module one of the types named needs, saying which. It gives what it makes to the user who ran it, and prints the number the kernel gave the GPIO chip and the IIO sensor. sudo bin/rm-kernel-stand-ins takes away whichever were made. Nothing either does survives a reboot.

Directory Description
can A motor controller on the CAN bus vcan0, as two payloads: its status frames, identifier 0x123, go to the ground, and each command the ground sends goes to it as one frame with identifier 0x124.
gpio Two lines of a GPIO chip: each edge of a switch on line 0 goes to the ground as a sixteen-byte record, and a 1 or 0 from the ground drives a lamp on line 1.
iio Experimental. A sensor’s sample buffer, read through the kernel’s IIO subsystem, its whole sample sets going to the ground. Nothing goes up: a buffer is read and never written.

can

vcan0 is the kernel’s virtual CAN bus: a bus with no wire, whose members are the sockets bound to it. tcspecial joins it as two of them, one for each identifier, and tcssim joins it as the motor, sending a status frame a second and counting the commands. On a vehicle the interface is the controller’s, such as can0, and nothing else changes.

make run-can

gpio

The chip is one of the kernel’s gpio-sim, whose lines exist in memory: a line’s pull file sets what an input is pulled to, which the kernel reports to tcspecial as an edge, and its value file says what an output is driven to. tcssim pulls the switch’s line the other way every second and counts the lamp’s changes. The configuration names /dev/gpiochip1, which is what the simulated chip is on a host with one chip of its own; the number is given as chips appear, so write the one bin/mk-kernel-stand-ins printed.

make run-gpio

iio

The sensor is one of the kernel’s iio_dummy, whose buffer a software trigger fills a hundred times a second: the kernel stands in for it entirely, and tcssim makes nothing. Its buffer is there only where the kernel’s iio_dummy was built with CONFIG_IIO_SIMPLE_DUMMY_BUFFER, which a stock distribution kernel’s is not; bin/mk-kernel-stand-ins iio says so where it was not, and that is why the type is still experimental. The configuration names /dev/iio:device1, which is what the dummy is on a host with one sensor of its own; write the number bin/mk-kernel-stand-ins printed.

make run-iio

Languages, for all three:

  • MOC: Rust – tcsmoc.
  • Vehicle: Rust – tcspecial.
  • Payload: the kernel’s stand-in, with tcssim playing the device’s far end for CAN and GPIO.

More complex examples

Each puts the vehicle to work on its payloads: what they send, and what is done with it aboard and on the ground.

Directory Description
thermostat Three temperature sensors, converted to kelvin, voted on, and fed to a hysteresis thermostat that drives two heaters, every one a UDP socket tcssim stands in for, so that it runs on any desk. The setpoint is commanded from the ground, and tcsmoc plots the temperatures and the heaters.
thermostat-yamcs The thermostat, with Yamcs as its ground station, over CCSDS packets: the zone’s temperature and the three readings arrive in Yamcs as temperatures in kelvin, and the thermostat’s decision as on or off, each a parameter the configuration types, and a Python 3 program shows them.
battery A power bus through an orbit: a power monitor asked over a serial line, a shunt, the battery’s charge counted by a Python 3 program, and the science load shed in eclipse by a hysteresis. tcssim stands in for every payload, joined to a physics model of a sun, a solar array, loads, a bus and a battery.
descent A lander’s terminal descent: a radar altimeter’s altitude flown down by a Python 3 guidance program throttling the engine, a Doppler velocimeter, and a touchdown switch that speaks the moment the lander is down. tcssim stands in for every payload, joined to a physics model of an engine and the body it brakes.
simple-app A payload that is a program rather than a device: an app_pl node sending a line of text one word per packet, and a ground station that prints the line. Two programs of its own beside the configuration: the payload in Python 3, the ground station in Rust.

thermostat

A control loop, aboard. Three temperature sensors are read together, once a second, as the group zone_temps: temp_1, temp_2 and temp_3. Each reading goes through a conversion of its own to kelvin – temp1, temp2, temp3, the parts differing in format and scale – and the three meet at ambient, which takes their median, so that one sensor failing cannot take the zone’s temperature with it. thermostat holds that to a setpoint, 293.15 K with a half band of 2 K, and drives two heaters, each through a GPIO line of its own, gpio-out-tmass1 and gpio-out-tmass2, which go on and off together. Its decision is logged and not sent down: what the ground hears is gpio-in-tmass, two lines on the thermal mass sensing the heaters, read for their levels every second, so the ground sees what the heaters are doing rather than what they were told. The ground commands the setpoint, and housekeeping logs the readings, the decisions and the lines in /tmp/telemetry.

The sensors are the far end of UDP sockets on this host, ports 5201 to 5203, which tcssim stands in for. The heaters’ switches and the lines sensing them are lines 2 to 5 of the kernel’s simulated GPIO chip, /dev/gpiochip1, which tcssim moves and watches: make it once with sudo bin/mk-kernel-stand-ins gpio (see “Payloads the kernel stands in for”, below). The gpio example has lines 0 and 1 of it, so the two run at once. Aboard the sensors would be on I2C and SPI, as tests/manual/thermostat.ytcs has them; those buses are flown against stand-ins by make stand-ins-test.

tcssim joins the stand-ins to the vehicle’s physics model, thermostat-common/thermostat-physics.yaml, which thermostat-sim.yaml names, as thermostat-yamcs’s simulator file does: a zone and two heaters, each a part simulated alone and joined to the zone under connections. All three sensors are joined to zone.temperature, each from a place of its own on the zone, so their readings agree and the vote produces a temperature. The zone starts at 292.15 K, inside the band, and cools towards its surroundings, 288.15 K, just inside the plot’s lower red, which swing half a kelvin over a ninety minute orbit; each heater’s switch’s stand-in is joined to heater_1.on or heater_2.on, so the heaters warm it while the vehicle has them on: the loop closes through tcspecial. gpio-in-tmass’s stand-in pulls its line 2 to heater_1.heating and its line 3 to heater_2.heating, which are on only while each heater is really heating. The heaters are four watts each, and either alone holds the band, the thermostat cycling whichever are working; a heater disabled in tcssim shows on its line’s strip, and with both disabled the zone falls into the plot’s lower red.

A heater whose switch’s panel in tcssim is not enabled is unpowered, or failed: it stays off whatever the thermostat decides, and enabled again it takes the latest decision at once. The ground sees it on its line of gpio-in-tmass, which stays low, and in the temperature.

make run-thermostat

That runs tcsmoc on the example, as run-simple does, and tcsmoc opens its plot window beside its own: each sensor’s temperature and their vote over the last ten seconds, a dot at each reading, with the setpoint’s rule and the thermostat’s band, and under them a strip for each line of gpio-in-tmass, gpio-in-tmass line 2 and line 3, on while its heater is heating. Press Connect in tcsmoc, and Enable on each payload in tcssim, to start the data and the heating; press Disable on a heater’s switch in tcssim to take it away, and its strip stays off while the zone falls behind in the cold part of the orbit.

Languages:

  • MOC: Rust – tcsmoc.
  • Vehicle: Rust – tcspecial, whose conversions, vote, thermostat and log are its own nodes.
  • Payload: Rust – tcssim stands in for the three sensors, with the zone they read, and for the heaters’ switches and the lines sensing them, on the kernel’s simulated GPIO chip.

thermostat-yamcs

The thermostat example with Yamcs at the ground end, as ping-yamcs is the ping example with it. The vehicle is the thermostat’s – the same sensors, conversions, vote, thermostat, heaters, GPIO lines and log, which tests/shared.rs holds to the thermostat example’s, and the same physics model, thermostat-common/thermostat-physics.yaml – and what differs is the configuration’s gateway, yamcs, so every packet to and from the ground carries a CCSDS primary header:

What Which way APID
the beacon down beacon.apid, 0x110
CONNECT and its answer up, down tcs_cmd.apid, 0x111
what Yamcs sends the gateway node up its apid_base, 0x400
ambient down apid_base plus its device id, 0x400
gpio-in-tmass down 0x402
temp1, temp2, temp3 down 0x406 to 0x408

thermostat_yamcs.py writes Yamcs’s configuration with python/tcslib/yamcs_ground.py, as ping_yamcs.py does, its mission database generated by python/tcslibgs/yamcs.py. That gives each node drawn into the gateway node a parameter of the type the configuration says its data are, by python/tcslibgs/form.py – the Python spelling of tcslibgs::graph::fprime::Form::of, which tcsmoc’s plot window and the F´ bridge go by, and nothing a configuration does not already state: a conversion’s or a vote’s value is a float in its unit, with the unit in a UnitSet, read from its four bytes of a signed count of the unit’s steps through a calibrator, and lines read for their levels are a record for each line, its level a boolean. So Yamcs’s web interface, at http://localhost:17090, shows ambient and temp1 to temp3 as temperatures in K and gpio-in-tmass_line2 and _line3 as true or false.

It starts Yamcs, then tcssim – every payload sending from the start, as though its panel’s button had been pressed – and, once tcssim says it is ready, tcspecial, each with --simulate=all; has Yamcs send CONNECT until the vehicle answers with the configuration’s checksum; and reads the parameters back over Yamcs’s REST API. Its window shows the beacon panel above the thermostat’s: the zone’s temperature, each reading, and each line sensing a heater, on or off. With --seconds there is no window: it prints every value each --every seconds, and a line each time a heater’s line changes, and stops. tcssim draws a window of its own, so either wants a display. Every payload sending from the start includes the heaters’ switches, so both start enabled; press Disable on one in tcssim’s window to take its heater away, and its line goes low and stays low while the zone falls behind in the cold part of the orbit. Its GPIO lines are the thermostat example’s, so the two are not run at once.

make run-thermostat-yamcs YAMCS_HOME=~/yamcs-5.14.0   # the window
python3 examples/thermostat-yamcs/thermostat_yamcs.py --yamcs ~/yamcs-5.14.0 \
    --seconds 120
python3 examples/thermostat-yamcs/thermostat_yamcs.py --describe

Yamcs, tcssim and tcspecial are stopped when it ends and killed with it if it is killed or crashes.

The Rust crate beside it is its tests: agrees.rs holds the ports, APIDs, forms and checksum thermostat_yamcs.py --describe reads from thermostat-yamcs.xtcs to what tcslibgs reads from thermostat-yamcs.ytcs, the Python’s form of every node of every example to Form::of, and its table of units to tcslibgs::unit; wrapper.rs works the generated mission database as Yamcs would, with examples/yamcs-common’s interpreter, on what the vehicle sends – each value as value_bytes makes it, in every unit there is, and each decision; shared.rs holds its vehicle and simulator file to the thermostat example’s; and python.rs runs test_thermostat_yamcs.py. None needs Yamcs or opens a window.

Its ports are all in the seventeen thousands, which no other example uses, so it can run beside the thermostat example.

Languages:

  • tcspecial configuration: YAML (thermostat-yamcs.ytcs) or XML (thermostat-yamcs.xtcs)
  • ground program: Python 3 (thermostat_yamcs.py), with Yamcs (Java)
  • payloads: Rust – tcssim, as in the thermostat example

battery

A spacecraft’s power bus through an orbit: the example of a payload that is asked, of a computation that is a program, and of physics with events in it.

monitor, a power monitor on a serial line at /tmp/tcs-battery-monitor, is asked for the bus voltage twice a second – its trigger is "V?\r" – and bus_volts makes its two bytes volts. shunt, the shunt in the battery’s lead, sends the battery’s current twice a second over UDP, port 5301, and battery_amps makes it amperes. charge is a process node running charge.py, a Python 3 program beside the configuration that counts the current coulomb by coulomb into the battery’s state of charge, a ratio, and sets itself full whenever the current falls to nought. shedding, a hysteresis around 0.4, sheds the science instrument below three tenths by driving science, port 5302, and restores it above half.

tcssim stands in for all three, joined to the vehicle’s physics model, battery-physics.yaml: a sun, a solar array, two loads, a bus and a battery, each a part simulated alone and joined under connections. The orbit is six minutes and the battery small, so that a run sees, in one orbit, the battery charge and fill, the eclipse drain it, the science load shed and the sun bring it back. Going into shadow and out, and the battery reaching full, are events of the model’s, met at their moments.

make run-battery

Press Connect in tcsmoc, and Enable on each payload in tcssim, to start the data.

Languages:

  • MOC: Rust – tcsmoc.
  • Vehicle: Rust – tcspecial, whose conversions, hysteresis and log are its own nodes – and Python 3, the charge count, which is a program of the example’s.
  • Payload: Rust – tcssim stands in for the power monitor, with a pseudo-terminal at its path, the shunt and the science switch.

descent

A lander’s terminal descent over the Moon: the example of a computation that drives a device with a value, and of a device that speaks the moment something happens.

radar, a radar altimeter on UDP port 5401, sends the altitude ten times a second, which altitude makes metres. guidance is a process node running guidance.py, a Python 3 program beside the configuration that works out the rate of descent from the altitudes, flies a rate that slows as the ground nears, and answers a throttle, a ratio, which drives engine, port 5404: four bytes of a value, which the engine’s stand-in reads as the ratio it is. doppler, port 5402, sends the velocity for the ground, and touchdown, port 5403, a switch on a landing leg, says 1 when the lander is down.

tcssim stands in for all four, joined to the vehicle’s physics model, descent-physics.yaml: an engine and the body it brakes, five hundred metres up and falling at twenty metres a second. The body falls by the rocket equation, and the moment it reaches the ground is found ahead of time and met exactly; the touchdown switch’s stand-in waits on the model for it, and speaks then. A run lands in about seventy-five seconds.

make run-descent

Press Connect in tcsmoc, and Enable on each payload in tcssim, engine and radar first: the lander does not start falling until a stand-in starts.

Languages:

  • MOC: Rust – tcsmoc.
  • Vehicle: Rust – tcspecial, whose conversions and log are its own nodes – and Python 3, the guidance, which is a program of the example’s.
  • Payload: Rust – tcssim stands in for the radar, the velocimeter, the switch and the engine.

simple-app

The one example that runs end to end on one host, and the one to look at to see what an app node is. Two programs, both in examples/simple-app:

  • lorem_pl.py is the payload, a Python 3 program that uses nothing outside the standard library. tcspecial starts it from the configuration, as the executable of the app_pl node named lorem, and runs it with the node’s name and app-payload-arg – which for this payload is the line of the text to send, counting from one. It sends one word per packet and then a packet holding the line terminator.
  • lorem_gateway is the ground station, a Rust program in the crate beside the configuration. It gets lorem’s words from the configuration’s gateway node, gateway-1, with one function call, tcslib::gateway::GatewayReceiver::receive_into, which works out from the configuration which port they arrive at and puts each word in a buffer made before the loop, so that the loop allocates nothing; it writes out each word with one space between them, and stops when the terminator arrives. Before its first word it sends a CONNECT of its own, carrying the configuration’s checksum, with tcslib::listening, and sends it again each second until the vehicle answers with that checksum: a vehicle sends nothing down until it has taken one, and nothing else in this example sends one. It sends it from the configuration’s tcs_cmd.send, so tcsmoc cannot be run on the same configuration beside it; -v says when it is matched.
make run-simple-app

That checks for Python 3, builds the vehicle and the ground station, starts the vehicle in the background and the ground in the foreground, prints the line, and then stops the vehicle. To watch the two separately, run them in two terminals instead, in either order:

cargo build                   # lorem_gateway and tcspecial
cargo run --bin lorem_gateway # in one terminal: the ground (--xml for XML)
cargo run --bin tcspecial -- examples/simple-app/simple-app.ytcs   # in another

Run the vehicle from the repository’s root, where the configuration’s executable path starts. Either order works because the payload waits a couple of seconds before its first word: the vehicle sends each word to the ground station’s address as soon as it has it, and a word sent before lorem_gateway is listening is lost.

The text itself is simple_app’s library: the first paragraph of the lorem ipsum text as one array per line, each holding that line’s words. Nothing holds a line terminator; the end of a word array is the end of the line, and what stands for it on the wire is the one constant both programs read.

Languages:

  • MOC: Rust – lorem_gateway, on tcslib::gateway.
  • Vehicle: Rust – tcspecial, which runs the payload as its app_pl node.
  • Payload: Python 3 – lorem_pl.py.
